# AI-native SDLC

本项目由 AI 承担需求整理、架构分析、实现、测试、技术审查、文档和交付准备。用户只需用自然语言描述目标，参与 UI、交互取舍和最终产品验收。普通且已经授权的任务按完整流程自主推进，不新增 intent、spec、plan 的逐阶段人工审批。统一规则见 [AI_RULES.md](../../AI_RULES.md)，需求转译见 [PROMPTING.md](PROMPTING.md)，Git 门禁见 [BRANCH-POLICY.md](BRANCH-POLICY.md)。

本文参考 [Claude AI-native SDLC playbook](https://claude.com/blog/the-ai-native-sdlc-playbook) 的版本化产物、反馈验证、独立审查和确定性门禁原则，并按本项目的个人仓库与多 AI 协作方式调整。可执行约束由 Git 托管规则、CI 和实际权限承担；Markdown 文件只能指导 AI，不能保证任意工具必然读取或不可绕过。

## 开始任务与职责

先读仓库根规则，再读 [治理入口](../governance/README.md)、[当前状态](../governance/PROJECT_STATE.md)、[规范索引](../governance/SPEC_BASELINE.md)、[任务账本](../governance/task-ledger.json)、相关 change package 和实现。核对当前 checkout、branch、HEAD、remote、worktrees、未提交改动及并行写入。聊天和历史测试记录不能替代当前事实。

AI 在 `intent.md` 保留用户原意，再转换为可执行工程描述，包含目标、范围、约束、数据和平台影响、验收方法、假设与未决项。可用中英文技术术语，不要求用户先写专业提示词。只有会改变产品行为的关键歧义、重大范围扩展、无法解决的有效规范冲突，或缺少必要授权/外部条件时才向用户提问；其他技术选型由 AI 查证后承担。对用户的最终说明使用简洁、通俗中文。

“已授权”必须引用实际用户请求或已有明确授权；AI 可以标记技术计划已就绪，不能替用户写“已人工批准”。同一授权在范围未变化时持续有效。

## 产物链与阶段门禁

每个 PR 在 `docs/changes/<date>-<task>/` 使用 [模板](../templates/intent.md) 新建本次交付包，所有文件共享 task ID 并相互引用；后续 PR 延续同一任务时用新日期或明确后缀，保留旧记录。普通小修的五份记录可各用几行完成；字段不适用时写原因，不要求用户代写或审批文书。

| 阶段            | AI 负责的产物                                                          | 继续条件                                                 |
| --------------- | ---------------------------------------------------------------------- | -------------------------------------------------------- |
| Plan            | `intent.md`：用户问题、原话/来源、工程转译、范围、可观察结果、关键假设 | 用户意图清楚，授权范围有依据；关键产品歧义已解决         |
| Design          | `spec.md`：状态/交互、数据与 API、平台能力、验收条件；必要时 ADR       | 符合现行规范；冲突和平台差异明确；验收可执行             |
| Build           | `plan.md`：文件、依赖、顺序、风险、验证、恢复；代码和测试              | AI 已读真实实现；工作隔离；有可验证的最小方案            |
| Test            | `verification.md`：当前源码和产物身份、命令、结果、运行态证据          | 适用门禁通过；未验证项明确；失败未被隐藏                 |
| Review / Deploy | `review.md`、PR、CI；发布时 `release.md`                               | 独立审查当前 SHA；满足实际托管规则；发布在用户授权范围内 |
| Maintain        | `incident.md`、回归/eval、账本和恢复入口                               | 异常有证据、负责人、恢复策略；后续工作回到 intent        |

实现与计划不符时同步更新 spec/plan 并重新判断风险；若改变用户产品意图，先解决语义分歧。AI 不因一个本地单测通过就跳过后续适用门禁。

artifact 可以用 DRAFT / READY / IMPLEMENTED / VERIFIED / RELEASED 标记自己的阶段；任务状态使用 `scripts/governance/ledger.mjs` 中的受控集合（TODO / READY / IN_PROGRESS / PARTIAL / REVIEW / BLOCKED / DONE / REGRESSION / OBSOLETE）。`task-ledger.json` 是任务状态权威，不能用 artifact 的 READY 或历史的 DONE 覆盖它。BLOCKED 只用于必要外部条件；代码失败先修复，缺证据写 NOT VERIFIED。

## 自主范围与高风险动作

| 情况                                           | AI 自主执行                                                     | 需要用户或外部条件的部分                                      |
| ---------------------------------------------- | --------------------------------------------------------------- | ------------------------------------------------------------- |
| 已授权功能或修复                               | 读代码、制定方案、改源码、隔离测试、补文档、独立技术审查        | 新增产品语义或重大范围扩展                                    |
| 数据、凭据、权限、存储、Provider、基础设施变更 | 风险分析、最小方案、源码实现、合成数据和 fixture 验证、恢复演练 | 未授权的真实数据删除/迁移、权限扩大、秘密配置、费用或外部写入 |
| Git 与发布                                     | 分支/PR 准备、冲突处理、检查、发布与回滚产物准备                | 遵守已存在的推送/合并/发布授权和托管门禁，不能替用户批准      |
| 监控与维护                                     | 在已授权范围只读诊断、复现和提出修复                            | 未配置监控、缺凭据/预算或需要真实外部操作时如实升级           |

高风险不等于每改一行都问用户；它要求更严格的隔离验证、恢复证据和独立审查。普通技术实现继续推进，真正依赖外部条件的验收独立入账。已确认过的授权不重复请求。

## 架构和多端生命周期

改变模块依赖、公共契约、平台职责、持久化格式、任务恢复语义、安全边界或重大依赖前，使用 [ADR 模板](../templates/adr.md) 在 `docs/architecture/adr/` 记录现状、方案比较、决定、代价、迁移与回滚。普通局部实现不用新增 ADR。

各端共享领域契约，平台能力在 spec 中逐项说明：Desktop 的原生文件/凭据/TaskHost、Web 的浏览器存储与受限能力、Mobile 的实际目标 runtime。不能把 390px 浏览器布局验收称为原生移动端验收。新增功能应覆盖安装或初始化、正常使用、版本升级、失败、取消、离线、进程重启、恢复以及退役/导出；不适用项说明原因。

架构记录要引用当前数据契约及相关测试，不能复制出另一个 source of truth。同一文件由多个任务修改时串行整合；独立任务使用独立 worktree。冲突修复和合并后必须重新验证实际整合结果，不能用两个分支各自通过代替。

## 证据、恢复与交接

review 绑定被审查的 base/head SHA；任何 head SHA 变化使旧批准失效，必须重新审查并记录新结果。测试和运行态证据仍然是旧 SHA 的历史事实；对新 SHA 要重新判断影响并执行相应检查，不能直接改写记录中的 SHA。源码或配置影响构建时重建实际被加载的 Web/Tauri 产物。

历史日志、截图、验证结论和已接受 ADR 保留；发现错误追加勘误，注明旧结论、纠正理由、时间、新证据和替代关系。不要覆盖失败日志、追改命令结果或把 fixture 改称 live。工具生成证据可能覆盖固定路径时，运行前转到新的带日期目录或另存本次输出；不能销毁唯一历史记录。

长任务中断后从账本、change package、Git SHA、实际进程/端口和构建产物恢复。交接写入 [AI_HANDOFF.md](../governance/AI_HANDOFF.md) 的恢复入口，不复制整段聊天；项目事实更新 PROJECT_STATE，已完成迭代更新 PROGRESS，任务归属/状态更新账本并生成 TASK_LEDGER 视图。

## 维护、监控与 eval

发布计划列出真实可读的健康指标、阈值、观测窗口、告警责任、恢复条件和 runbook。阈值判断尽量使用确定性检查；AI 用于诊断和提出修复。记录“监控计划”“已配置”“已运行”三种状态，未经部署和运行证据不能声称监控已经生效。自动回滚仅执行预先授权且演练过的 runbook。

事故和重复问题用 [incident 模板](../templates/incident.md) 保存时间线、影响、根因、恢复、后续任务及回归用例。规则、提示词、模型或工具变化时，用有预期结果的真实任务样例检查需求理解、数据安全、审查与交付行为。确定性 guardrail 测试和真实模型 eval 分开报告：前者通过不等于模型行为通过。

live eval 必须记录模型/版本、规则版本、任务集合、预算上限、权限、运行 ID、结果和失败样例。缺少合法凭据或费用授权时可以准备样例和检查器，但标记 live eval 为 NOT RUN，不用 mock 结果冒充。以后是否增加自动化和运行频率由授权预算与实际风险决定。

定期查看返工率、严重 review 问题、生产逃逸缺陷、恢复时长和同类事故复发情况；这些数据用于改善规则和测试，不用代码量或“全部完成”的自述证明质量。
