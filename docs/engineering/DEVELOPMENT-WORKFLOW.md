# 开发协作流程

本文件是日常开发的操作入口。它把 [SDLC](SDLC.md)、[分支与工作树规范](BRANCH-POLICY.md)、[测试规范](TESTING.md)、[评审规范](REVIEW.md) 和任务账本串成一条流程；专项规则仍以各自文档为准。

## 1. 任务领取

任务状态唯一记录在 [`docs/governance/task-ledger.json`](../governance/task-ledger.json)。`TASK_LEDGER.md` 是生成视图，不手工维护；功能状态继续由 `features.registry.json` 和功能卡承载。

领取前完成以下检查：

1. 读取 `AGENTS.md`、`AI_RULES.md`、[`docs/README.md`](../README.md)、项目当前状态、任务账本、相关功能卡和相邻 change package。
2. 检查当前 branch、HEAD、remote、worktree、dirty/index 状态和正在运行的端口；确认没有重叠的写入者。
3. 选定一个 Task ID，登记 owner、branch/worktree、base SHA、依赖、影响模块、共享文件和整合负责人。
4. 在 `intent.md` 写清用户原意、目标、非目标、数据/平台范围和可观察验收条件。
5. 记录基线测试、预存失败、外部条件、权限/费用边界和恢复入口。

没有 Task ID、负责人、验收条件、文件归属和基线证据时，任务保持 `TODO`，不能直接开始修改。现有任务必须复用，不能为同一问题重复建卡。

## 2. 需求和验收确认

开工前逐项确认：

| 项目 | 必须回答的问题 |
| --- | --- |
| 用户结果 | 用户完成什么操作后，能观察到什么变化？ |
| 范围 | 哪些入口、平台、数据和模块包含在本次任务？明确不包含什么？ |
| 验收 | 每条 AC 如何观察、用什么命令或运行证据证明？ |
| 依赖 | 哪些任务、服务、凭据、Provider、权限或用户决策必须先具备？ |
| 风险 | 数据迁移、秘密、费用、不可逆动作和回滚条件是什么？ |
| 未决项 | 哪些是 `UNKNOWN` 或真正需要用户决定的产品语义？ |

关键产品语义、权限、数据迁移或范围扩展没有答案时，相关部分进入 `BLOCKED`，并记录阻塞责任边界、解除条件和下一次检查时间。普通技术选型由执行者查证并记录，不把推断写成用户已经确认的需求。

## 3. 状态流转

账本状态使用脚本允许的集合；日常协作含义如下：

| 状态 | 含义 | 进入条件 | 退出条件 |
| --- | --- | --- | --- |
| `TODO` / 待领取 | 尚未登记开工证据 | 已有目标、来源和初步范围 | 领取人补齐开工字段后进入 `IN_PROGRESS`，必要时进入 `BLOCKED` |
| `IN_PROGRESS` / 进行中 | 正在设计、实现或验证 | owner、worktree、依赖、AC 和基线已登记 | 实现与自查完成进入 `REVIEW`；外部条件缺失进入 `BLOCKED` |
| `REVIEW` / 待复核 | 交付包和验证已准备，等待复核/验收 | 当前 SHA、diff、验证结果和遗留项已记录 | 全部门禁通过进入 `DONE`；缺陷退回 `PARTIAL`/`IN_PROGRESS` |
| `DONE` / 已完成 | 实现、适用回归、文档、独立复核和用户可观察验收均有证据 | 完成标准全部满足 | 发现回归进入 `REGRESSION` 或 `PARTIAL`，保留原证据 |
| `BLOCKED` / 阻塞 | 必要外部条件、决策或权限未满足 | 记录原因、影响、责任边界、解除条件 | 条件满足后回到 `IN_PROGRESS`，不能直接跳到 `DONE` |

`READY` 用于计划可执行；`PARTIAL` 表示部分完成或证据不足；`REGRESSION` 表示已完成范围出现回归；`OBSOLETE` 表示任务被明确废弃。状态变化必须同时更新账本和 change package，理由与证据要短而具体。`TASK_LEDGER.md` 的 `Status` 列读取账本真实状态；`Display` 列是既有三档摘要，不能用它替代 `Status` 判断 `REVIEW` 或 `BLOCKED`。

## 4. 实施和开发笔记

一个任务对应一个 dated change package。小修仍创建五份记录；不适用的文件写明原因。开发过程中只记录会影响复现、决策或交接的内容：

```text
时间：YYYY-MM-DD HH:mm TZ
状态：旧状态 -> 新状态
事实：实际观察、命令结果或文件/版本身份
决策：选择了什么方案，依据是什么，放弃了什么
影响：文件、模块、数据、平台和并行任务
验证：命令、退出码、证据路径、限制
遗留：未验证项、阻塞条件、后续 Task ID、回滚入口
```

需要长期保留的架构取舍写 ADR；故障写 `incident.md`；计划变化写 `plan.md` 的变更记录。不要覆盖历史失败日志，不要把旧 SHA 的结果改写成新 SHA 的通过证明。

## 5. 完成说明

进入 `REVIEW` 时，负责人提交一段可直接交接的成果说明：

- 改了什么，用户现在能做什么；
- 影响哪些文件、模块、数据和平台；
- 运行了什么检查，退出码和证据在哪里；
- 哪些能力仍是 `PARTIAL`、`NOT VERIFIED` 或依赖外部条件；
- 遗留任务、回滚触发条件和恢复入口是什么。

完成说明不等于完成判定。只有适用的实现、用户验收、回归、文档/账本同步和独立复核都具备当前 SHA 证据时，才可把任务标记为 `DONE`。

## 6. 验证检查清单

### 变更前

- [ ] 需求、范围、AC 和用户授权已记录。
- [ ] 规则、账本、功能卡、相关实现和相邻交付包已读取。
- [ ] branch/worktree、HEAD、dirty/index、依赖和运行端口已记录。
- [ ] 预存失败、并发写入者和恢复方案已记录。

### 实现后

- [ ] 格式、类型、单元/集成/构建和专项治理检查按适用范围执行。
- [ ] 真实 diff 已 self-review；命名、重复实现、边界处理、错误和权限路径已复查。
- [ ] 空输入、异常响应、取消、重试、超时、离线、重启、旧数据、重复提交、stale response、Provider 未配置和错误回执已按功能覆盖或说明不适用。

### 交付前

- [ ] `verification.md` 绑定实际 base/head/tree SHA、工具版本、命令、退出码和限制。
- [ ] UI/桌面任务记录真实运行入口、端口、bundle/exe/profile 身份；fixture 不写成 live。
- [ ] 独立 review 绑定当前 head；head 变化后重新复核，不复用旧批准。
- [ ] 账本、功能卡、`PROJECT_STATE.md`、`AI_HANDOFF.md`、`PROGRESS.md` 和交付包已同步。
- [ ] 用户产品验收、Hosted CI、发布和外部 Provider 状态分别记录，未发生的写 `NOT VERIFIED`。

## 7. 失败、根因和防复发

发现问题立即按以下顺序处理：

1. 保存原始失败和当前身份，先复现，不先改测试或删日志。
2. 缩小范围，区分代码缺陷、环境/依赖问题、数据问题和外部条件。
3. 写出已证实根因及排除的假设；必要时建立 `incident.md`。
4. 用最小改动修复，先补能复现问题的回归检查，再重跑原失败命令。
5. 复查相邻边界，记录规则、监控、测试或交接上的防复发措施。

`unknown`、数据不一致、取消未确认和服务端状态不明不能用普通重试掩盖；没有证据就保持 `NOT VERIFIED` 或 `BLOCKED`。

## 8. 竞品迭代节奏

每周做一次短观察，每两周做一次路线复盘；忙时可顺延，但要保留日期和原因。竞品材料进入 [`docs/reference/competitor/INDEX.md`](../reference/competitor/INDEX.md) 或对应研究 change package，至少记录：对象、日期、观察模式、来源、证据、静态/运行/账号/费用边界。

已跟踪品类的共识基线、学习优先级（L0–L3）与转化闭环见 [`COMPETITIVE-LEARNING-POLICY.md`](COMPETITIVE-LEARNING-POLICY.md)（2026-10-26 制定，首个跟踪品类为 AI 短剧/视频创作工作台）；该方针是本节的品类化展开，不改变本节的节奏与证据要求。

复盘分三层：

1. **外部事实**：只写可复核的页面、安装包或公开说明。
2. **本地差距**：映射现有 feature/task，说明是否值得做实验；不复制竞品 CSS、模型池或服务端假设。
3. **候选动作**：最多列三项，每项写目标、AC、依赖、成本、放弃条件和验证方式。

静态比较、截图、本地 fixture 或竞品未运行时都不能提升 KK 的完成度。只有通过本地实现、适用运行验证和交付门禁，候选动作才进入正常任务流。

## 9. 持续改进

每周任务整理时查看状态停留时长、返工率、重复缺陷、P0/P1 review 问题、生产逃逸、恢复时长、未验证项积压和竞品观察转化率。指标用于减少等待、合并重复任务、补边界测试和更新规则；不以代码量或“全部完成”自述替代证据。

发现同类问题重复出现时，必须把修复落到至少一个可执行位置：确定性检查、回归测试、模板字段、ADR/incident 规则或交接清单，并在下一个相邻任务中复查是否生效。
