# 评审规则

评审验证当前变更是否满足用户意图、遵守架构和数据边界，并有足够证据交付。AI 承担技术审查；用户确认 UI、交互和最终产品结果。先做 self-review，再由独立上下文复核，不能让实现者的一句“已通过”充当 review。分支保护与实际审批要求见 [BRANCH-POLICY.md](BRANCH-POLICY.md)。

## 评审身份与 SHA

reviewer 从当前 `intent/spec/plan`、适用规则、base/head SHA 和真实 diff 独立开始；不要只接收实现者摘要。可使用新的只读 AI 上下文或具备独立审查能力的 reviewer，记录其工具/模型（能获取时）、审查时间、范围和证据。没有独立上下文时标记 independent review 为 NOT VERIFIED，不能把 self-review 改名。

实现者负责修复，reviewer 复核修复。实现 AI 不得批准自己的 GitHub PR；同一个 GitHub 身份的多个 AI session 仍是同一身份。个人仓库不强制虚构第二名人类：实际 ruleset 不要求第二人时，以真实独立 AI 审查、CI 和已有用户授权履行流程，并如实记录人工审批数量；若实际规则要求另一人批准而无法满足，则该合并门禁未满足。不能伪造审核账号、绕过有效规则或把 AI 评论称为人类 Code Owner approval。

每次 review 记录 base SHA、head SHA 和规则版本。head SHA 一变，原 review 对新提交失效，需重新审查；目标分支更新时重核合并结果与相关测试。旧结果保留，不能直接改 SHA 让旧结果继续有效。只有已提交变更可出正式最终 review；dirty diff 的 review 只是预检。

## 必查范围

| Pass           | 重点                                                                                                            |
| -------------- | --------------------------------------------------------------------------------------------------------------- |
| 用户意图与范围 | intent/spec/plan 的验收逐项满足；产品语义未被猜测或扩大；技术计划变更有记录                                     |
| 行为与回归     | 主路径和相邻流程；输入边界；错误、取消、离线、超时、stale async、焦点/Escape/IME；幂等、重试与 unknown 受理边界 |
| 架构与平台     | 职责/导入边界；共享契约与 Desktop/Web/Mobile 能力差异；兼容、schema、升级、恢复与必要 ADR                       |
| 安全与数据     | 密钥、授权、输入校验、文件路径、日志、原件保护；失败不能变空数据或假成功；新增依赖、权限和外部传输有依据        |
| UI 与可用性    | 适用的最新 Figma 同状态、tokens/共享组件、实际 route/import 链、动态长文案、窄屏、键盘与可访问性                |
| 验证与交付     | 当前 SHA 的命令/结果；Web 与 Tauri 实际产物新鲜度；PR/CI/远端门禁；发布、备份与回滚证据                         |

不要重复报告格式器或 CI 已明确指出且仍等待修复的同一条问题。生成文件只检查来源和最终影响；安全或运行行为不能因“生成文件”而免审。

## 严重度与阻断条件

严重度描述影响；`merge-blocker` / `release-blocker` 描述实际门禁，分别记录。

| 严重度 | 定义                                                           | 处理                                                              |
| ------ | -------------------------------------------------------------- | ----------------------------------------------------------------- |
| P0     | 正在发生或高度确定的严重数据泄露、不可恢复破坏、广泛生产不可用 | 立即停止相关发布/危险操作、保护证据并修复；禁止用风险签字代替关闭 |
| P1     | 关键路径错误、数据/权限/迁移/恢复风险、关键平台退化            | 默认阻断合并或发布，修复并由 reviewer 复验                        |
| P2     | 局部缺陷、有限回归或维护性问题                                 | 有界修复；非阻断遗留须入账并解释为何不影响本次验收                |
| P3     | 低影响改进或可选建议                                           | 不阻断；最多列五条，避免淹没真实风险                              |

失败的必需 CI、未满足的实际托管审批、未解决的关键验收或有效规范冲突、密钥暴露、伪造成功、弱化测试以通过、缺少高风险恢复证据、缺少实际发布授权，都是阻断条件。不能通过改低严重度解除门禁。已接受的明确范围调整需要先更新需求及验收依据，重新 review；未关闭 blocker 不得标 PASS。

每条 finding 写：稳定 ID、P0–P3、pass、是否阻断/阻断哪一步、文件/行或证据、可复现条件、影响、建议处理、负责人、状态和复验结果。没有实际证据的担忧标为待调查，不能伪装成已复现缺陷。

## 证据要求

按 [DEVELOPMENT.md](DEVELOPMENT.md) 和任务计划读取实际检查结果。命令/日志要有退出码、来源 SHA、环境、时间和路径；reviewer 应抽查关键失败路径，必要时重跑与风险直接相关的测试。没有运行工具时明确“仅静态 review”，不声称动态验证。

UI 证据包含同状态 DOM/截图、Figma 节点、视口、URL/模式、入口和构建身份；Web development、production preview 和 Tauri release 分别取证。测试的 HTTP fixture 只证明 fixture 范围；真实 Provider/ComfyUI、账号/账单、GPU、原生重启、生产部署须各自有真实验收。缺这些证据只阻断依赖它们的结论，不能把整个项目其它本地工作冻结。

修 bug 应先复现失败再修复。review 检查是否删除、跳过、放宽断言或滥用重试使测试变绿；测试确有错误时记录独立依据并增加有效覆盖，不能盲目禁止合理测试维护。历史证据不覆盖、不伪造；更正追加勘误并链接替代结果。

## 高风险审查

数据删除/导入/迁移、凭据和权限、持久任务/付费提交、用户文件、生产配置/发布及恢复等变更需要额外检查：备份与还原实证、异常输入、失败不破坏原件、原子性/并发、取消和重启、最小权限与费用上限。高风险源码与隔离测试仍由 AI 自主完成；真实外部执行依照当前授权和相应门禁。

## 结论与记录

使用 [review 模板](../templates/review.md)，分别记录 self-review、独立 AI review、CI、实际 GitHub 审批、用户产品验收和发布授权。只保留真实存在的结果，不互相代填。

- `PASS`：本次审查范围没有未关闭 blocker；适用证据完整并绑定当前 SHA。
- `PASS WITH FOLLOW-UPS`：没有 blocker，遗留 P2/P3 有明确任务、影响说明和负责人。
- `CHANGES REQUIRED`：存在需要修复或补证的代码/验收问题；继续工作，不滥用任务 BLOCKED。
- `NOT VERIFIED`：独立性、证据或当前 SHA 复核不足。
- `BLOCKED`：必要外部条件或实际托管门禁缺失；写明解除条件。

review PASS 只代表已审范围，不代表已合并、已发布、用户已验收或完整产品已达到 MUR。
