# 项目缺口与本次处置

本次目标是让 AI 能持续、可核查地负责工程。用户负责产品意思、UI/交互和最终体验验收；AI 负责把口语变成工程任务并执行。参考 [Anthropic AI-native SDLC playbook](https://claude.com/blog/the-ai-native-sdlc-playbook) 的分阶段产物、确定性检查、独立审核和持续改进思路，按现有项目约束落地，没有照搬其特定工具或服务。

| 发现                                                            | 风险                                     | 本次处置 / 仍需完成                                                                                                      |
| --------------------------------------------------------------- | ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| 不同 AI 入口不一致，用户被迫写技术提示词                        | 换工具丢失边界、反复解释                 | AI_RULES、PROMPTING 与五类工具入口统一；12 个口语反例场景。静态检查只能验证入口/结构，不能保证模型理解                   |
| 规则与实际存储、UI 阶段和生成调用链漂移                         | AI 依据过时规范继续扩写                  | 修正现行规范；补 JSON/TS 缺失的 tasks 目录，与已有 Rust 定义核对；旧 UI 节点和前端阶段标为历史                           |
| 原工作区有大量并发改动，旧本地 main 与新远端无共同祖先          | 拉取/重置误删成果或重复整合              | 新任务从 origin/main 创建隔离 worktree；保留原现场；分支核对清单独立留档                                                 |
| 分支要求停留在文字层                                            | 误 force/delete/direct push              | 安装 common pre-push、真实临时 repo 回归；准备服务器 rulesets。服务器当前 403 套餐限制未解除                             |
| 单用户仓库照搬“一个人批准”无法执行                              | 自审批或假造审核                         | PR + 当前 CI + 独立 AI 上下文审核 + 用户结果验收；独立账号出现后才能启用账号审批要求                                     |
| CI 不检查当次交付包                                             | 只有代码，缺验收和交接                   | delivery job 检查当次 verification/review、变更包、账本/进度及禁入路径；这是结构门禁，不证明评审质量                     |
| 当前 main CI 动画测试漏采中间帧                                 | 主线长期红灯，失去质量信号               | 保留几何断言，暂停并采样真实 CSS transition 时间点；修复依据与结果分别记录                                               |
| 浏览器测试覆写历史截图与报告                                    | 旧证据被新结果污染                       | 截图改 test.info().outputPath，JSON 写 test-results；CI 上传当次产物；历史目录恢复原字节，新增静态防复发检查             |
| Desktop 原生提交绕过 Web 连接 reservation，失败 health 字段丢失 | 禁用/冷却/并发约束可能在原生提交窗口失效 | 已核实代码路径并将实现修复、租约崩溃恢复和 IPC 验收纳入 T5；尚未修复，不准宣称桌面全门禁已完成                           |
| “本地通过”容易被当作真实服务或多端完整交付                      | 用户误判可用能力                         | Web/原生桌面/Mobile、fixture/live 分别验收；真实 Provider、ComfyUI、安装恢复仍按现有任务保留缺口                         |
| 只有开发规则，没有升级/事故/运维闭环                            | 发布后难以回滚、同类故障反复             | 新增 ADR/release/incident 模板、恢复要求和 eval 场景；生产监控、外部安全扫描和付费模型评估尚未部署，模板不等于已运行能力 |
| “只保留最新”缺少精确定义                                        | 删除历史后无法找回完整项目               | 最新稳定入口 + 完整 main；不可变版本标签、PR/历史、上一可用产物和备份保留；清理必须核对 squash PR 和分支当前 head        |

不能据此声称整个产品已完成：本次完成的是治理实现、有限契约修复与当前证据校正。发布仍需关闭相关产品任务、真实平台验收和外部门禁。当前状态以 ledger 与本次 verification 为准，所有结论带范围。
