## 1. 背景与目标

### 1.1 现状问题

KK-Studio-2.0 存在多条执行/配置路径、多份元数据与缓存、五个模型接入 tab，以及未被前端生产源码调用的旧 Tauri 命令。第 9 章按职责列出 A～G 七组资产，它们并非七条等价的生成通路；存储也应按权威元数据、秘密、运行状态和偏好区分，不能把它们一概视为重复数据库。

当前 37 条 feature 中有 2 条 REAL（画布、素材库），**不代表统一模型接入已经 REAL**。同地址同名账号身份冲突、Provider 状态镜像、来源汇总和生产调度接线仍有缺口。现有保存流程已有跨窗口协调、原生锁、CAS 和凭据失败补偿，收敛时必须保留。

用户侧的直接感受是「**加账号麻烦、切模型麻烦、看不到额度**」。

### 1.2 目标

建立**一套**统一接入层：用户添加任意来源的模型账号后，模型统一汇总到选择器，额度统一可见，多账号自动轮换，接口对调用方保持一致。

### 1.3 成功判据

| 判据 | 可验证的标志 |
|---|---|
| 加账号简单 | 五种添加方式收敛为「一个列表 + 五种方式」 |
| 切模型简单 | 用户选模型**不必先知道模型在哪** |
| 额度可见 | 显示上游报告的剩余额度与采集时间；未提供时显示未知，**区分订阅/网页额度与 API 额度** |
| 多账号可用 | 在模型、权限和任务约束允许时选择账号；仅确认未受理的任务可自动切换，已受理或受理未知的任务不重放 |
| 不臃肿 | 每项业务规则和每类数据各有唯一权威；共享契约与入口，保留必要的宿主适配及各层边界校验 |

|---|---|---|

#### 3.2.1 Codex 多账号（S1 的关键子需求）

**问题**：当前 `codex.ts` 是单一 client、串行队列和活动线程；未实现按账号/profile 管理的执行上下文。多账号不能只增加目录，模型、额度、线程、审批、取消和结果事件都必须绑定同一身份。

**需求**：
- 支持管理多个 Codex 登录身份，每个身份绑定真实独立的 `CODEX_HOME`；KK 只保存非秘密 profile 引用与账号摘要
- 复用官方 app-server 的执行实现，每个 profile 独立 client/队列；同一 profile 的登录、执行和认证生命周期由一个官方进程管理
- 主 Agent 会话与线程固定身份；账号池只对允许自动路由的子任务选号，不接管或迁移运行中的主会话
- 单身份额度耗尽时，仅对确认未受理的子任务尝试下一个合格账号；已发出受理请求且状态未知、已产生输出或工具副作用时禁止换号重放
- 身份与模型对照：每个身份可用模型不同（受订阅档位影响）
- 通过官方 `account/read`（普通查询不强制刷新）、`model/list` 和 `account/rateLimits/read` 读取账号摘要、模型与额度；迟到响应不能覆盖另一身份，查询失败保留 unknown/stale

**锁定版本事实与隔离约束**：

1. 仓库锁定 `@openai/codex 0.155.1` 的 CLI 凭据默认值是 **File**，默认 Auto 的是 MCP OAuth；keyring 的身份也与规范化 `CODEX_HOME` 绑定。**不能据“全局凭据必覆盖”的错误前提强制改为文件存储**，具体来源见附录 C。
2. KK 不读取、复制、注入或刷新 CLI token，不以复制 `auth.json` 建池。官方 CLI 自管认证文件与 KK 自持秘密是不同所有权；受管 profile 的存储模式、目录权限及与仓库安全规则的兼容须在实施前明确，不能因官方默认 File 就自动采用明文回退。
3. 同一 session 的刷新应串行；官方进程内同步不能作为跨进程保证。KK 的 profile 所有权锁只约束遵守它的 KK 实例，不能宣称能阻止用户手工 CLI 刷新。不得为 S1 再建一套 KK token 刷新 worker。
4. 多账号并行必须隔离环境、线程、审批、取消与归档；同 profile 双实例竞争、进程异常退出和锁释放都须验证。

#### 3.2.2 Antigravity 接入（方案 2）

**已确定的架构决策**：采用**方案 2** —— KK spawn 官方二进制，**不自己持有登录态**。

| | 方案 1（否决） | 方案 2（采用） |
|---|---|---|
| 做法 | KK 直接调本地服务接口，自持登录态 | KK 像跑 Codex 一样 spawn 官方二进制 |
| 身份所有权 | KK 自持或复制厂商登录态，边界不符本需求 | 官方进程管理自己的认证，KK 只驱动受支持的进程接口 |
| 可用性依据 | 本需求不采用 | 仍须核实该产品的官方 CLI、授权范围和可用协议；spawn 本身不能证明已获支持 |

**实施要点**：
- 模板：现有 Codex 通路的 spawn 模式 + stdout 事件出口 + **凭据零注入**
- 先核实官方 CLI 身份、版本、安装位置和可调用协议，再扩展 `CliTool` 与本地二进制发现；不把桌面程序或猜测路径当作可执行适配器
- **前置**：用户安装并登录受支持的官方 CLI；原候选路径 `C:\Users\<user>\AppData\Local\agy\bin` 仅作待核实线索
- **待实测**：该 CLI 的语言服务器疑似**随机端口 + 私有 RPC + 进程参数 token**，若属实则不适合长期驻留，改为「随用随起」生命周期

### 3.3 S2 — OAuth 订阅账号

**范围**：具有可供本应用使用的正规客户端授权流程的平台。ChatGPT / Claude / Gemini / Grok / Kimi 是候选来源，不能因存在登录页面就宣称支持第三方 OAuth 或可使用其订阅额度。

**需求**：
- 授权 URL 生成（含 **PKCE** 与 **state 校验**，防 CSRF）
- 回调接收（localhost 临时服务器或 deep-link）
- token 存入 **Windows 凭据管理器**（access / refresh / expiry 三要素）
- 只有 KK 正式持有 S2 授权时才实现相应刷新生命周期；同一 session 的刷新在同机多实例间串行。若由官方进程管理认证，则复用该机制，不再由 KK 重复刷新
- 刷新失败降级：标记「需重新授权」并在界面提示

**首批平台建议**：先核验 OpenAI 正式 Sign in with ChatGPT 路径是否适用于 KK 的分发形态，再确定 S2 首批平台。官方目前区分开源/本地应用与付费/远程托管应用；应用注册、用户 consent、scope 和模型权限均须验证，不能拿已有 Codex 登录态替代 S2 授权（见附录 C）。

**边界**：正规 OAuth 采用官方公开协议；非公开内部端点不作为默认前提。订阅登录、网页会话和普通 API Key 计费独立，不共享或猜测权限。

### 3.4 S3 — 网页登录（无头抓 token）

**已确认的范式**（用户明确：「无头浏览器只用于登录和抓 token」）：

```
启动 debug Chrome（隔离 profile）
  ↓ 人工登录（首次或会话失效后）
  ↓ Playwright / CDP 附着，抓取 cookie + bearer token
  ↓ 存入 Windows 凭据管理器
  ↓ 之后直接调用内部接口，不再驱动浏览器
```

**核心特征**：浏览器只用于登录与会话捕获，不在每次生成时点击网页。此方式仍依赖会话、接口和授权机制，不能承诺不受网站改版影响；只接入已确认允许且完成真实适配的平台。

**需求**：
- 支持多个网页账号并存（用户有 2 个订阅账号）
- token 失效检测与重新抓取引导
- 与 S2 一致地复用凭据管理器

**平台可行性判断准则**（供后续扩展自查）：

必须分别验证：**本应用可用的授权方式、目标接口协议、额度归属和实际执行能力**。底层模型有公开 API，并不证明网页订阅能用于该 API，也不证明网页 token 可被重用于它。

| 网页形态 | 底层有 API？ | 结论 |
|---|---|---|
| 开发者平台型（AI Studio） | 公开开发者接口 | 验证 S4 凭据、权限与计费，不推定消费级订阅可用 |
| 消费级外壳型 | 接口/计费可能独立 | 优先核验正规 S1/S2；普通 API Key 不自动使用网页订阅额度 |
| 有客户端型（Antigravity） | 桌面客户端不证明 CLI 可用 | 先验证官方 CLI 与协议，再走 S1 方案 2 |
| 纯黑盒网页 | 未证实可调用接口 | S3 后置验证；不可用时明确禁用，不以底层模型同名推断可接入 |

### 3.5 S4 — API Key 账号

**现状**：已有 5 种文本协议的前端与 Rust 实现及既有验证记录；通用 BYOK 图片主链目前仅支持 OpenAI Chat 对应的图片接口，独立 Google 图片链另存。本轮未重跑真实 Provider。

**需求**：
- 保留现有能力
- **修复缺陷**：同一 baseUrl、同一显示名称的新账号会派生相同身份；新账号使用不可变 ID，编辑名称不改变身份，旧 ID/凭据引用继续可解析（见 D1）
- 额度显示：有上游查询接口则读取；没有则显示未知。可展示已观测 token 用量，不能据此估算剩余余额或以价格表换算金额

### 3.6 S5 — API Key 中转站

**现状**：已有中转/自有实例预设与通用表单，但能力需按各实例实际协议和模型声明；部分预设地址为空。账号池、持久轮换与生产调度尚未接通，不能视为现成多路 failover。

**需求**：
- 预设补全用户实际在用的中转站
- 支持同一中转服务多实例并存
- 参与统一选号调度

### 3.7 S6 — 本地模型

**现状**：LM Studio / Ollama 预设及本机免密文本已支持，未找到品牌级整体 `disabled`。真实缺口包括首页仅接图片、未知用途模型禁用、视频/音频执行器未接、`local_comfyui` 未进入同一选择器，以及通用提交拒绝免密图片。应逐项补接线，不全局解除禁用。

**需求**：
- 在统一选择器中可见可选
- 标注「本地 · 无上游额度限制」（简写「无限」仅指无上游额度，不代表算力、并发或可用性无限）
- **自动路由默认本地优先**；仅在模型/能力、健康与任务约束满足时参与，不覆盖用户显式选择的来源或模型

**预设补全**：vLLM、Jan。

## 4. 功能需求

### FR1 地址自动匹配（R10）

**需求**：用户在供应商表单输入 baseUrl 时，自动识别对应的预设。

**三态返回**（关键设计决策）：

| 状态 | 触发条件 | 界面行为 |
|---|---|---|
| 无匹配 | 未知地址 / 非法输入 | **不提示**（不强行推荐） |
| 唯一匹配 | 命中且仅一条 | 提示「识别为 X（协议 Y）」+ **填入按钮** |
| 多匹配歧义 | 命中多条 | 提示「同时匹配 A 与 B，协议不同，请手动选择」+ **不给按钮** |

**硬约束**：
- **绝不静默修改**协议与认证字段 —— 会使连接已有的生成验证状态被重置为「未验证」
- 填入仅在用户**显式点击按钮**后发生
- 歧义场景**不提供任何按钮**，确保不可能触发字段写入
- 填入按钮须明示副作用：「填入将清空当前未保存的 API Key，并使本次编辑重新检查凭据与连接验证状态」；不得仅因匹配或填入就删除 vault 秘密、重建已保存账号 ID 或改写旧凭据引用。新账号引用按不可变账号 ID 分配
- 保留的是原账号已提交的记录与秘密，不代表授权向新端点复用。baseUrl 或认证受众变化时，编辑草稿必须解除旧凭据的自动可用绑定；测试/发送前须显式重新绑定或提供适用凭据，宿主同样校验绑定，失败保留原连接。不得凭稳定 ref 把旧秘密自动发往变更后的地址

### FR4 额度可见（R6）

#### 4.1 两栏显示（关键设计）

**订阅/网页额度与普通 API 计费必须分栏记录**。同一家或同一登录身份不代表两栏可以互用；只有上游正式授权明确允许时，S1/S2 才使用对应计划额度，不能把它记成普通 API 余额。

```
示例账号 A（非平台实际额度承诺）
├── 订阅/网页额度   上游报告值 / 未提供
└── API 额度        上游报告值 / 未查询 / 未开通（仅有明确证据时）
```

**需求**：界面必须分栏显示，避免用户看到「我有订阅为什么 KK 说没额度」。

#### 4.2 各接入源的额度来源

| 接入源 | 额度形态 | 获取方式 |
|---|---|---|
| CLI（Codex） | 按官方报告的 bucket 与窗口，不硬编码所有账号都有 5h/周窗口 | 已有 CLI 读取链路；需补账号归属与快照持久化 |
| CLI（Antigravity） | 窗口与模型维度待官方接口核实 | 受支持的官方报告接口；缺失则未知 |
| OAuth 订阅 | 按正式授权可读取的计划窗口 | 官方账户/usage 接口；缺失则未知 |
| API Key | 上游可查询余额/限额，或仅观测 token 用量 | 上游接口；不得按 token 推算剩余余额 |
| 中转站 | 面板余额 | 中转站 API |
| 网页登录 | 网页额度 | 网页会话 |
| 本地模型 | **无上游额度限制**，本机容量与健康另行记录 | 不虚构额度总量、余额或百分比 |

#### 4.3 额度元数据（不换算金额）

**需求**：额度记录包含账号、账本类别（订阅/网页或 API）、窗口/bucket、上游值、重置时间、采集时间与未知/过期状态，**不做金额换算**。`usedPercent` 是已用比例；显示剩余时须正确换算，nullable 不作为 0。不同窗口或单位不能相加/直接比较，稀疏更新不能清空已有无关窗口。

理由：主流网关项目为此硬编码了数百 KB 的价格表，模型一更新就要同步；且上游控制台已有价格，KK 再维护一份会造成**权威分裂**。

```ts
quota: { kind: "rpm" | "rpd" | "tpm" | "balance" | "credits" | "window"; label: string; resetHint?: string }
```

### FR6 账号轮换策略（R4）

| 策略 | 行为 | 来源 |
|---|---|---|
| `round_robin` | 按**上次选中身份**推进轮询（非数组下标） | 参照项目 |
| `fill_first` | **刻意烧穿一个账号再换下一个**，最大化单窗口利用率 | 参照项目 |
| `weighted` | 按权重分配 | 已有内核资产，尚需生产接线 |
| `quota_aware` | 仅比较同一额度维度内的新鲜快照，优先剩余较多的；未知时按已配置策略降级 | 参照项目 |
| `local_first` | 在允许自动路由且能力兼容的候选中优先本地 | 新增 |

上述策略均须可配置、持久化并被生产入口消费。候选先按权限、模型、能力、健康和并发过滤，持久化必要的身份游标/冷却/人工介入状态；同一请求不重复尝试已失败账号。主会话绑定、用户显式选择和已冻结任务不被策略覆盖。CLI/HTTP 可以有不同执行适配器，不各自重写选号规则。

**round_robin 的关键实现要点**：

> 轮询必须按「上次选中身份」推进，不能按数组下标。重试排除已试凭据或凭据进入冷却时，候选切片会收缩 —— 把单调计数器索引到收缩中的切片会**静默重置轮询位置**，导致部分凭据饿死、部分被反复 hammering。

**fill_first 的适用场景**：滚动窗口配额**按账号独立重置**时，让单个账号的窗口配额一次性用尽再切换，避免「每个账号都只用 5% 就被切走」的浪费。

### FR7 错误分类与冷却

| 类别 | 冷却策略 | 自动恢复 |
|---|---|---|
| 速率突增（RPM） | 短冷却（`15s × 2^(n-1)`，封顶 2 分钟） | ✅ |
| 配额耗尽（RPD/日限额） | 长冷却（对齐重置时间窗） | ✅ |
| 认证失败 | **永不自动恢复**，标记「需人工介入」 | ❌ |
| 计费问题 | **永不自动恢复**，标记「需人工介入」 | ❌ |
| 超时 | 短冷却（5 秒）；受理未知另行冻结，不自动重提 | 冷却可恢复不等于原任务可重放 |

**必须支持的错误识别**：

- `RESOURCE_EXHAUSTED` 不凭单一字符串直接判为长期耗尽；结合结构化错误、限制维度和重置信息区分速率/额度，证据不足保留未知原因
- `Retry-After` 响应头须处理秒数/日期、无效值和异常值，通用提示**硬顶 24 小时**；已核实的额度重置时间单独保存，到达通用提示上限不代表真实额度已恢复
- **冷却探针**：有受支持且无生成副作用的健康/额度查询时，可在到期前最多 2 分钟探测，短冷却不高频探测；查询失败不阻塞主流程，不以付费生成作为默认探针
- 认证失效与明确计费问题持久化为需人工介入；普通冷却到期不自动解除。请求参数/内容拒绝不能通过换账号反复重试
- 调度失败动作与任务受理状态分别判断：已开始流、已受理、受理未知、已有工具副作用或取消未确认时，均不得自动换账号重放

### FR8 界面不误导（R14）

**需求**：不可用能力必须给出**准确**的文案，不得暗示不存在的路径。

现状中存在“适配器文件已写，但生产入口未消费”的资产。账号登录通路不可用与 API Key 通路是否可用须分别核实；不能凭适配器行数、模型目录或笼统的品牌提示证明实际生成能力。

**文案规范**：不可用来源的提示须指向**真实可操作的路径**。

## 7. 数据需求

### 7.1 存储选型

**需求**：统一账号元数据、额度观测、用量流水与策略的数据库持久化；秘密不进入数据库，不新增服务端账号/支付系统。

**现状**：桌面 Provider 配置是 JSON + revision/CAS、原生锁和备份恢复；Web Provider 元数据是 localStorage。仓库独立 `generation-server/repository.ts` 已使用 Node 内置 `node:sqlite`，具备事务、连接状态、租约和日志；这不等于桌面 Provider 已接入 SQLite，也不意味着 Web 当前已使用 IndexedDB 存 Provider。

**桌面目标**：SQLite 单文件、零外部服务；通过现有原生仓库/命令边界承载事务、索引、策略游标和并发租约。Rust 驱动尚未引入，实施前论证驱动与版本，保留已有 CAS、恢复与错误语义。可借鉴 Node 仓库的事务/租约实现，不照搬其价格、充值或多租户账本。

**Web 目标**：与桌面共用账号仓库契约，在对应平台交付阶段使用 IndexedDB 持久化；允许宿主实现不同，不维持另一套业务模型。按 Desktop → Web → Mobile 门禁推进，本任务不实现 Mobile。Desktop 切换不以提前完成 Web 数据库迁移为前置，现有 Web 行为须保持可用。

数据库事务不天然覆盖 OS 凭据库；必须沿用并验证跨仓库失败补偿。额度是上游快照，数据库不通过本地“扣减”变成额度权威。

**明确排除**：PostgreSQL / Redis（违背单机定位，引入体积与运维负担）。

### 7.2 核心表

| 表 | 关键字段 |
|---|---|
| **connection** | 不可变账号 ID、来源类型、显示名、可选 baseUrl、协议、认证方式、凭据/profile 引用、并发上限、可恢复租约、冷却、人工介入状态、优先级、负载因子、revision；显示名不参与身份 |
| **credential** | 凭据元数据：所属账号、所有权（KK/官方进程）、秘密引用、已报告的到期信息、是否需重授权；不解析 CLI auth 文件补字段 |
| **quota_snapshot** | 账号、账本类别、bucket/模型适用范围、窗口与单位、上游报告的总量/已用/比例（均可未知）、重置时间、抓取时间与数据状态 |
| **usage_log** | 账号、项目/会话/任务引用、模型、请求标识、受理状态、输入/输出 token（未报告则未知）、耗时、终态与时间；不含提示词、凭据、原始响应或金额 |
| **model_entry** | 账号 × 模型：模型 ID、显示名、上下文窗口、能力 |
| **route_policy** | 策略配置：作用域、策略、参数、启用状态、必要的上次选中账号游标与 revision |

字段是统一逻辑契约，不要求全部状态硬塞进一个对象。新账号使用不可变 ID；**已有账号 ID、credentialRef、Google 固定连接、模型目录和冻结任务绑定不自动重建**。CLI 不要求 baseUrl，来源类型、认证方式与执行协议分开建模，现有 `ConnectionKind` 与 `ChannelKind` 不做不等价的机械替换。

### 7.3 关键设计决策

**额度数据的定位**：KK 侧存的是**观测快照**，**权威账本在上游**。

只在本机事务化记录观测、租约、路由和用量，不自行推算余额、补充额度或对外形成价格权威。查询失败保留带时间的旧快照并标过期/未知；不能用新账号的查询结果覆盖旧账号。

### 7.4 单一权威与迁移

| 数据 | 权威归属 | 迁移/兼容要求 |
|---|---|---|
| 连接、模型目录、调度状态、额度观测 | 统一账号仓库；Desktop SQLite，后续 Web IndexedDB | 前端仅为可重建投影；保存/删除/health/lease 等所有写入走同一仓库接口 |
| API Key、KK 正式持有的 OAuth/网页凭据 | OS 凭据库；Web 仅请求/会话内存，其他方案另行定义 | 数据库只存引用；不写 localStorage、项目、URL、日志或导出 |
| 官方 CLI 登录与刷新 | 官方进程及受管 profile | KK 只保存非秘密引用，不读取/复制 auth 文件，不向数据库导入 token |
| 选择器记忆、置顶与页面偏好 | 原偏好契约 | 保留原 key、旧 selection/pins 的兼容；不当作账号元数据权威 |

- 默认保留原连接和已知 `credentialRef`，按引用定向解析；无枚举接口不代表全部重填。只有缺失或无法确认的引用提示补充，不删除孤儿凭据或整库。
- 凭据引用与其已确认的端点/认证受众绑定。迁移保留原绑定；变更地址不能仅沿用稳定 ID/ref 就自动发送旧秘密，须按 FR1 重新确认适用绑定；UI 与原生/执行边界都要防止跨受众误发。
- 原生已有权威优先于旧缓存；旧浏览器数据只在满足一次性迁移条件时导入，迁移可重入且不重复建账号。损坏、歧义、权限错误须保留原件并反馈，不能静默丢弃或用缓存覆盖新权威。
- SQLite 导入提交后需核对账号/引用/revision 和恢复结果，再切换读写；不能长期维持双向镜像。明确提交失败、vault 失败、投影刷新失败和进程中断的恢复/补偿边界。
- 旧配置可能含明文是风险，**本轮未读取用户配置，不能宣称实际存在或已经清除**。将来定向迁移已知字段须有安全恢复方案；不为备份再输出一份明文秘密，不静默清理未知文件。

### 7.5 秘密存储（不进入数据库）

- KK 自持的 API Key / OAuth token / 网页会话秘密在 Desktop 使用系统凭据库（Windows 为凭据管理器），或仅在请求内存中使用；Web 不因加入数据库就持久化秘密
- S1 认证由官方 CLI 自己管理，KK 不持有 token；不能把官方存储文件迁入 KK 数据库，profile 的存储模式和目录权限需满足第 3.2.1 节及现行安全规则
- 数据库、普通配置和导出只存非秘密引用；保留嵌套秘密字段拒绝、URL 校验、日志/回执脱敏及失败补偿

## 8. 隔离需求

### 8.1 六个维度

| 维度 | 现状 | 需求 |
|---|---|---|
| **同源多账号** | credentialId 有账号参数，但新账号按地址＋可编辑名称派生身份 | 新增不可变账号 ID，编辑不换身份，旧 ID/ref 保留 |
| **上游凭据 vs 下游访问 Key** | 独立网关与 Provider 语义不同 | 明确分层、不混用；不为桌面新增虚拟 Key/入站计费系统 |
| **官方/中转/部署来源** | 官方和中转表单有内存草稿隔离，但共享持久 profile | 同一账号仓库按来源分类，记录所选账号 ID；不新增两套完整 profile 镜像 |
| **账号级** | 多处身份/目录/状态绑定不一致 | 每账号凭据/profile 命名空间和模型、额度、任务绑定一致 |
| **日志脱敏** | 需确认 | 用量流水只记 token 数与耗时，**绝不落凭据** |
| **进程级** | 当前 Codex 是单 client，现有 Agent/CLI 锁不等于 profile 或刷新锁 | 受管真实 profile 路径、进程所有权、环境与事件隔离；明确 KK 锁不约束外部手工进程 |

### 8.2 隔离的语义与边界

本需求同时覆盖三种隔离，不再作为互斥备选：
- 凭据不串（不同账号的密钥不混）
- 数据不串（不同项目的用量不混）
- 故障不扩散（一个账号出问题不影响其他）

**验收边界**：账号 A 的密钥、额度和模型不进入 B；项目/会话/任务用量保持原归属；A 故障不阻断其他合格账号的新任务，但不得重放 A 已受理或受理未知的任务。主会话身份、审批、取消与归档的归属不能随选号变化。

## 9. 架构约束

### 9.1 三条收敛原则

| | 原则 | 反面 |
|---|---|---|
| **P1** | **不删有价值的能力**，换位置承载 | 因「看起来是死代码」就删掉能跑的东西 |
| **P2** | **每项业务规则与每类数据各有唯一权威**，宿主差异通过适配器承载 | 各入口各自维护账号、选号、额度和错误规则 |
| **P3** | **收敛 ≠ 膨胀** | 旧文件加开关继续共存 |

**「不臃肿」的判定**：统一连接/调度/状态契约与可达入口，复用既有执行能力；必要的 Web/原生 IO、官方 CLI 协议适配以及每个信任边界的 URL/DNS/权限校验保留。共用契约测试，另补宿主与生产接线测试，不以“一套测试”删减验证。

### 9.2 现有执行/配置资产的处置

| 路径 | 内容 | 处置 |
|---|---|---|
| **B** | 多通道调度网关资产 | 复用为调度内核；当前 src 未构造 Scheduler/ChannelRegistry，须在真实提交入口实接线并验证 |
| **E** | Rust 原生任务宿主 | 🟢 **提升为桌面执行内核** |
| **D** | 浏览器直连 | 🟢 **保留为 Web 路径** |
| **F** | Agent / CLI / Google | 保留受支持的官方进程/专用适配，接入统一契约；Codex JSON-RPC 不另写进 Rust |
| **C** | 独立网关进程（含计费/配额/并发闸门） | 先吸收所需事务、租约和恢复能力并核实调用方，再按退役验收下线；不搬入价格/充值/多租户功能 |
| **G** | 供应商配置落盘链 | 🟡 **重接线，消除双向镜像** |
| **A** | 旧 Rust 直接 HTTP / 配置等命令 | 核实调用/兼容依赖和替代链路后归档，禁止重新启用旧明文配置；不按“零前端调用”直接删除全部原生命令 |

**目标**：Web 直连与 Desktop 宿主适配为两类平台边界，内部统一账号与调度契约；Desktop 官方 CLI 继续通过 Node Agent 驱动，不强行把 stdio、HTTP 和现有 bridge 改成同一传输。以真实调用方迁移及能力回归证明收敛，不能用删除到“两条”的数量代替验收。

### 9.3 四维唯一化

| 维度 | 现状 | 目标 |
|---|---|---|
| 协议与调度 | Web / Rust / Google / 网关存在重复和未接线资产 | 共享协议声明、业务规则与状态/错误契约，明确执行归属；宿主边界校验不删除 |
| 存储 | 配置、秘密、运行状态、缓存和偏好分散 | 每类数据一个权威（第 7 章），取消持续双向镜像，不把 vault/CLI 秘密/偏好塞入同一库 |
| 数据模型 | ConnectionKind、ChannelKind 等语义不同 | 统一账号/来源/能力契约并作兼容映射，不机械合并不同含义的枚举 |
| UI | 五处入口 | **一套** |

### 9.4 调度内核分层

```
调用层：现有生成/Agent 入口（统一请求、受理、结果与取消契约）
    ↓
Router（共享策略）：会话绑定 / 合格账号选号 / 安全重试 / 冷却 / 额度感知
    ↓
Access：KK 自持凭据按引用解析；CLI 认证由官方进程管理
    ↓
执行适配：Web HTTP / Desktop 任务宿主 / 官方 CLI app-server 或 bridge
    ↓
账号与模型投影：实际身份、模型、有效能力及额度状态
    ↓
账号仓库：元数据 / 额度快照 / 用量流水 / 策略与恢复状态
```

当前生产生成入口位于 `App.tsx` 的 `submitNativeTask / generateText / generateImages`，Codex 入口进入现有 Agent。`Scheduler` 或 `createGenerationAdapter` 有源码/测试不代表这些入口已消费；每次迁移须证明实际请求经过新链路，保留原任务幂等、冻结绑定、取消和重启恢复语义。

## 12. 交付分期

### 12.1 分期原则

- **原使用优先级不变**：第 2.2 节的八项排序是来源交付顺序，不能把 Codex 多账号与其他 CLI 捆成一批，或以 API 全量重构阻塞主 Agent。
- **只前置必要共同地基**：先完成账号身份、权威仓库、可恢复迁移和任务受理契约；不要求先重写全部协议、全部 UI 和全部策略才交付 Codex。
- **每期有实际消费与独立验收**：各来源随自己的阶段进入同一账号列表、选择器和额度投影，不能以未消费的 schema/适配器或可点击占位入口交付。
- **按来源逐步收敛**：调度、预设、能力声明和 UI 是共享工作，不再作为先于所有来源的大改造关卡；复用实现随对应来源接线，实际迁移后撤旧入口。
- **外部条件独立记账**：OAuth 注册资格、CLI 安装/登录或受支持接口缺失时保留准确的未验证/阻塞状态，可继续无依赖的技术准备；不改变原优先级，也不把缺少真实验收的来源标完成。
- **平台顺序不变**：先完成 Desktop 对应最小链路，再按共享契约推进 Web 同态验收；Mobile 不在本任务实现范围。
- **本轮仅修订本文件**：以下 TASK、数据库、UI、退役和数据迁移均为未来实施要求；不在本轮登记台账、修改其他文档/代码、安装依赖或新增目录。

### 12.2 Stage 划分

| Stage | 内容 | 对应需求 / 使用优先级 | 独立价值 |

```

来源交付：Stage 2 Codex 主 Agent

          → Stage 4 本地模型
```

箭头中 Stage 0→1 是共同技术前置；Stage 2～9 表达**使用优先级与交付顺序**，不代表每个来源都依赖上个来源的全部实现。Stage 10 的退役动作逐项依赖对应替代链路验收，不能因其他来源尚未完成就提前删除。

### 13.2 门禁验收

产品实现阶段按受影响范围执行以下必要检查，交付前还须通过完整 `npm run verify`；Rust/原生检查不包含在 verify 内，按变更补跑，不能删减有效断言或借重试掩盖失败：

```
npm run typecheck
npm test
npm run lint          # --max-warnings 0
npm run ui:check      # 无新增颜色字面量
npm run client:check  # Rust 侧
```

Rust 改动另跑 cargo test / fmt；UI 改动记录当前源码启动命令、实际 route/import chain、bundle/运行模式和同状态 DOM/截图；Web 与 Tauri 分别验收，不用旧包或单端截图代替。实际外部调用仅在相应账号/权限/费用授权下执行，未执行须记 NOT VERIFIED。

**跨阶段共同回归**：

- 数据：旧账号 ID/ref/selection/pins/冻结任务可恢复；重复迁移不重复建账号，损坏或写失败不覆盖原件。
- 任务：重复提交、迟到响应、取消未确认、未知受理、部分结果和进程退出不重复生成、不跨账号回写。
- 策略：受理与冷却状态分别判断；认证/计费人工介入不被普通到期探针自动解除；本地优先不覆盖显式选择。
- 额度：两栏账本、账号/模型/bucket 归属、采集时间、nullable、过期和窗口更新正确，无 token→金额或余额推算。
- 安全：秘密不入数据库/localStorage/项目/URL/日志/导出，边界 URL/DNS/权限校验保留；CLI 不读取或复制 token。

## 14. 风险登记

| 风险 | 影响 | 缓解 |
|---|---|---|
| **授权/协议条件不成立或端点变更** | 某来源无法实施或运行失效 | 优先正规公开协议，逐来源核实应用资格、版本与实际能力；未完成保持禁用/未验证 |
| **账号会话互踢** | 同一 session 并发刷新失效 | S1 官方进程单一所有者，KK 不另建刷新器；S2 按正式协议协调刷新，不把 KK 锁说成能约束外部手工 CLI |
| **网页改版** | 网页登录通道易碎 | token 失效检测 + 提示重抓；集中选址点便于快修 |
| **账号风控** | 高频自动化可能触发限制 | 控制并发；命中限制立即降级不重试风暴 |
| **模型跟进官方 API 化** | 订阅转 API 的动机消失 | 通道可插拔，不绑定单平台 |
| **凭据泄漏** | 账号被盗 | KK 自持秘密用系统凭据库/请求内存；CLI 由官方进程管理并核验 profile 存储与权限；普通存储/日志无秘密，旧文件按安全迁移方案处理 |
| **迁移或跨库提交中断** | 旧引用失效、vault 与数据库状态分裂 | 默认保留 ID/ref 和原件；可重入迁移、CAS、补偿与重启恢复，不把投影失败当作未提交 |
| **受理未知时自动换号** | 重复生成、重复工具副作用或结果写错会话 | 受理状态独立于错误/冷却；保持任务与账号绑定，禁止未知或已输出任务自动重放 |
| **架构臃肿** | 越改越乱 | 每类数据/业务规则唯一权威，来源分期消费共享实现；Stage 10 最终退役回归，保留必要宿主边界校验 |

## 附录 A：术语表

| 术语 | 含义 |
|---|---|
| **接入源（Source）** | 一个能提供模型的凭据单元 |
| **连接（Connection）** | 接入源 + 端点配置 + 凭据引用 |
| **模型条目** | 连接 × 模型 |
| **两本账** | 同一家同一订阅的网页额度与 API 额度相互独立 |
| **方案 2** | 驱动官方进程而不自持 token |
| **架构 A/B** | A = KK 自持/复制厂商登录态直接模拟客户端（本需求不采用）；B = 驱动官方进程（仍需核验授权与协议） |
| **烧穿（fill_first）** | 刻意用尽一个账号的窗口配额再切换 |
| **观测快照** | KK 侧按账号/账本/窗口记录的上游额度数据，非本地计费或扣减权威 |
| **受理未知** | 请求可能已被上游接收但未取得可靠回执；保留原任务/账号，禁止自动新建或跨账号重放 |
| **单一权威** | 每类数据与业务规则各有明确所有者，不要求秘密、CLI 状态和 UI 偏好落在同一个物理库 |

## 附录 B：本文档的决策来源

本文档保留原需求的产品方向，并按本轮源码/官方资料修正实施约束：

1. 范围确认：地址匹配 + 预设补全 + UI 统一全做

6. CLI 类采用方案 2

12. 旧账号默认保留迁移；每类数据一个权威；CLI 认证由官方进程管理；已受理/受理未知/已有副作用的任务禁止自动换号重放
