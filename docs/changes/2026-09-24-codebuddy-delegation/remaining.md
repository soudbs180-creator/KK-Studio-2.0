# 设计师 Agent 完整链路：后续验收顺序

1. **主控与记忆**：先完成 `TASK-MEMORY-001/002` 的 Web 真实目录授权、Desktop 新包运行、真实 Codex 对话引用；只认 KK Studio 内 Codex 路径，跨应用共享需各自受支持的适配器与文件读写联调。
2. **CodeBuddy 委派**：有限短文本从 KK Desktop 的真实 Codex 对话经 MCP/CLI 返回已验收，详见 [验证](verification.md)。下一步降低简单任务约两分钟的主 Agent 前置推理延迟，建立是否委派的可解释规则与回退；不要把 CLI 认作 WorkBuddy 原生 OAuth。
3. **WorkBuddy 原生连接**：按 [官方开放平台](https://open.workbuddy.cn/docs/third-party-app)申请第三方应用权限与 OAuth，再用获批应用验证账号授权、任务提交、取消、结果和额度。未获批前保持不可用。
4. **豆包与千问**：豆包网页当前地区限制，`dbb` 登录与模型列表均未通过；取得可用的官方访问路径（如火山方舟 API 与用户授权）后另建受限适配器并真实联调。千问桌面登录不自动授予 KK 调用权限，先查受支持接口。
5. **设计资产**：花瓣/Pinterest 先实现用户授权的收藏导入或浏览器显式选择，记录来源、链接、授权范围、风格标签与本地资产 ID；下载原件、批量同步及额度调配须逐站验证权限与许可。素材引用与生成任务绑定在 KK 自有资产库，不把外部页面当数据库。
6. **任务调配**：建立统一的任务能力声明、可用状态、成本/时延上限和结果回执。简单短文本可建议 CodeBuddy/低成本模型，复杂设计编排由 Codex 保持主控；用户可覆盖路线。自动路由必须通过真实对照任务证明质量、延迟、失败回退和花费，再开放默认启用。
7. **一致的设计体验**：在现有 KK Design System 中统一连接状态、审批、耗额、任务进度、错误和重试；从「导入风格参考 → 画布生成 → 资产归档 → 回看记忆 → 再生成」做跨 Web/Desktop 的完整验收。Octop 等开源项目只提取能力和设计原则，逐项改造成 KK 协议、状态与 UI，不直接堆入独立子应用。

每一项按 `可配置 → 真实请求 → 可见回执 → 失败恢复 → 资产/记忆归档 → 新包复测` 留证。未通过阶段标记 PARTIAL 或 NOT_VERIFIED。
