# 开发协作流程设计

- 日期：2026-10-10
- 状态：SELF-REVIEWED（等待用户复核设计说明）
- 关联：`docs/governance/task-ledger.json`、`docs/engineering/SDLC.md`、`docs/engineering/BRANCH-POLICY.md`

## 背景

项目已经具备任务账本、交付包、分支与工作树、验证和独立评审规范，但日常执行入口分散。任务领取、需求确认、成果说明、根因修复和竞品观察容易变成口头约定，增加重复实现、状态漂移和未验证完成的风险。

本设计把现有规则串成一条可执行闭环，保持 `task-ledger.json` 为任务状态唯一事实源，不新增第二套看板或产品运行时状态。

## 目标

1. 让每项工作都有明确的 Task ID、负责人、工作树、依赖、范围、验收标准和当前证据。
2. 统一任务状态及允许的流转，阻止没有需求确认或验证证据的“假完成”。
3. 让成果、决策、根因、遗留问题和复测结果在变更包中留下短而可追溯的记录。
4. 用固定周期的外部观察把竞品变化转化为经过筛选的假设、决策或任务，不把静态比较误报成产品能力。

## 非目标

- 不替换 `task-ledger.json`、功能注册表、SDLC、分支/工作树或评审规范。
- 不新建独立项目管理系统，不把 Markdown 汇总视图变成状态源。
- 不因竞品出现某项能力就自动承诺实现，不把 fixture、静态截图或本地模拟当作 live、发布或用户验收。
- 不改变当前并发中的产品源码、数据格式或运行时行为。

## 方案与文档边界

新增 `docs/engineering/DEVELOPMENT-WORKFLOW.md` 作为日常操作入口，引用而不复制专项规范：

| 问题 | 唯一承载位置 |
| --- | --- |
| 任务状态、负责人和依赖 | `docs/governance/task-ledger.json` |
| 用户意图、范围与验收 | `docs/templates/intent.md` 和本次 change package |
| 分支、工作树、基线与文件所有权 | `docs/engineering/BRANCH-POLICY.md`、`WORKTREE-LIFECYCLE.md` |
| 设计、实施、验证、评审和事故 | 对应现有模板及 `SDLC.md` |
| 竞品外部观察 | `docs/reference/competitor/INDEX.md` 及研究 change package |
| 项目当前事实和进展 | `PROJECT_STATE.md`、`PROGRESS.md` |

现有模板只增加操作所需的最小字段，不另造平行模板。`docs/README.md` 增加入口链接，`SDLC.md` 增加闭环引用。

## 状态机

账本使用现有受控状态集合；面向协作的中文含义如下：

| 状态 | 含义 | 进入条件 | 离开条件 |
| --- | --- | --- | --- |
| `TODO`（待领取） | 未分配或尚未具备开工证据 | 已有目标、来源和初步范围 | 负责人、worktree、依赖、验收标准和基线确认后进入 `IN_PROGRESS` |
| `IN_PROGRESS`（进行中） | 正在设计、实现或验证 | 已完成开工检查并登记归属 | 实现和自查完成进入 `REVIEW`；必要外部条件缺失进入 `BLOCKED` |
| `REVIEW`（待复核） | 产物已完成，等待独立复核或用户产品验收 | 交付包、验证记录和当前 SHA 已更新 | 证据满足完成门禁进入 `DONE`；发现问题退回 `PARTIAL`/`IN_PROGRESS` |
| `DONE`（已完成） | 实现、适用验证、复核、文档和验收均有证据 | 完成标准全部满足 | 发现回归进入 `REGRESSION` 或 `PARTIAL`，保留原完成记录 |
| `BLOCKED`（阻塞） | 必要外部条件、决策或权限未满足 | 可从 `TODO` 或 `IN_PROGRESS` 进入；记录阻塞原因、影响、责任边界和解除条件 | 条件具备后回到 `IN_PROGRESS`，不得无证据直接标记完成 |

`READY`、`PARTIAL`、`REGRESSION`、`OBSOLETE` 继续按账本脚本语义使用。每次状态变更必须同步账本和变更记录；生成的 `TASK_LEDGER.md` 只能通过脚本更新。

## 任务领取与开工门禁

领取人先读取根规则、治理入口、未完成任务、相关功能卡、相邻 change package 和当前 Git/worktree 状态，再在账本中登记：

- Task ID、负责人、目标 branch/worktree、base/head SHA；
- 用户原意、目标与非目标、可观察验收条件；
- 依赖任务、共享文件、并行写入者和冲突处理人；
- 数据、凭据、Provider、费用、外部系统及不可逆动作边界；
- 基线测试结果和已知预存失败。

开工前必须确认需求和验收标准。关键产品语义、权限、数据迁移或范围扩展不清楚时暂停相关部分并进入 `BLOCKED`/待决策；普通技术选型由执行者查证后记录，不重复请求已经存在的授权。

## 实施、成果说明与变更笔记

每个任务使用一个 change package。小修也要有简短的 `intent/spec/plan/verification/review`，不适用的文件写明原因。完成说明至少包含：

1. 改了什么，以及用户可观察到的结果；
2. 影响的文件、模块、数据和平台；
3. 执行过的命令、真实结果、当前 SHA 和证据路径；
4. 未验证项、外部条件、剩余风险和后续任务；
5. 如需回滚，触发条件和恢复入口。

关键决策写入 ADR 或 spec；故障写入 incident。不得覆盖历史失败日志或把旧 SHA 的结论改写成新 SHA 的通过证明。

## 验证检查清单

验证分为四层，完成任务时按适用项逐项记录：

1. **变更前**：确认需求/AC、读取规则、检查 dirty/worktree/依赖、保存基线失败。
2. **实现后**：运行格式、类型、单元/集成/构建和专项治理检查；复查命名、重复实现、错误处理、权限和数据边界。
3. **边界与恢复**：按功能检查空输入、异常响应、取消、重试、超时、离线、重启、旧数据、重复提交、stale response、Provider 未配置和错误回执；涉及 UI/桌面时记录实际运行入口、端口、bundle/exe 身份。
4. **交付前**：self-review 真实 diff，独立 review 绑定当前 SHA，更新账本、功能卡、PROJECT_STATE/HANDOFF/PROGRESS 和交付包；确认用户验收与发布授权没有被本地测试替代。

失败处理遵循“复现 → 缩小范围 → 证明根因 → 最小修复 → 添加回归 → 重跑原失败命令 → 记录防复发措施”。不能用重试次数掩盖 `unknown`、数据不一致或未验证状态。

## 竞品迭代节奏

每周做一次短周期观察，每两周做一次路线复盘；实际频率可因任务压力调整，但每次必须有日期、对象、观察模式、来源和证据。观察分为：

- 外部事实：只记录可复核页面、安装包或公开说明；明确静态、运行、账号和费用边界。
- 本地差距：映射到现有 feature/task，不直接复制竞品术语、CSS、模型池或服务端行为。
- 决策候选：只有当差距符合项目目标、数据安全和可验证范围时，才转成 ADR、假设实验或新任务。

每次复盘输出最多三项优先动作，并为每项写目标、验收、依赖和放弃条件。没有运行证据的竞品结论保持 `NOT VERIFIED`，不提升产品完成度。

## 完成标准与度量

任务只有在实现、用户可观察验收、适用回归、文档/账本同步和独立复核均有证据时才标记 `DONE`。持续改进每周查看：状态停留时长、返工率、重复缺陷、P0/P1 评审问题、生产逃逸、恢复时长、未验证项积压和竞品观察转化率；指标用于调整规则和测试，不用于虚构完成度。

## 验收条件

| ID | 可观察结果 | 证明方式 |
| --- | --- | --- |
| AC-1 | 新成员能从文档入口完成任务领取并知道何时可开工 | 阅读流程指南和模板，检查任务字段与状态表一致 |
| AC-2 | 状态变更不再依赖口头约定或第二套看板 | `task-ledger.json` 为唯一状态源，生成视图可重建 |
| AC-3 | 每项完成工作都有成果、验证、遗留问题和当前 SHA 记录 | change package 模板包含对应字段，治理/Markdown 门禁通过 |
| AC-4 | 失败问题会形成根因、回归和防复发记录 | verification/incident 模板与流程清单覆盖完整闭环 |
| AC-5 | 竞品观察不会被误报为产品能力或发布证据 | 竞品目录与流程明确外部事实、本地验证和未知边界 |

## 风险与取舍

- 文档增加可能造成阅读负担：通过单一入口、最小模板字段和“短记录优先”控制。
- 状态仍可能被手工绕过：继续依赖账本脚本、交付检查和当前 SHA 复核；不声称 Markdown 能强制所有工具。
- 竞品观察可能变成无效信息流：限制观察输出数量，并要求每项映射目标、证据和放弃条件。
- 当前根工作区有并发源码改动：本次实施只写治理文档，验证时单独记录预存 dirty 状态。

## 设计自审

- **权威性**：没有新增状态源；任务状态继续由 `task-ledger.json` 承载，`TASK_LEDGER.md` 继续是生成视图。
- **范围**：方案只涉及流程文档、模板和索引，未改变产品源码、数据格式或运行时行为。
- **一致性**：已对照 SDLC、分支/工作树、评审、测试和竞品目录；新增流程引用这些规范，不重写其既有门禁。
- **状态完整性**：覆盖待领取、进行中、待复核、已完成、阻塞和回归；阻塞可在开工前或实施中发生。
- **验证边界**：明确区分本地、外部、live、发布和用户验收，保留 `NOT VERIFIED` 语义。
- **待用户确认**：若接受本设计，下一步只生成实施计划；计划仍需按本设计限定文件范围，并在执行后跑文档与治理门禁。
